# 运维审核阻断项整改

Status: ready-for-human

第一版部署交接文档送审后，运维给出「不通过」结论并列出七类阻断问题。本票记录逐条整改与实测证据。
文档不承载这份缺陷清单——运维手册只描述目标状态，缺陷归这里。

## 背景

审核结论：可读性 7/10，可操作性 4/10，上线审核不通过。

## 一、`TRUST_PROXY=loopback` 无效

**运维判断成立，且比他描述的更复杂。**

用最小 Fastify 实例实测，请求源为 Docker 网关、带 `X-Forwarded-For: 203.0.113.9`：

| `trustProxy` 取值 | `req.ip` | `req.protocol` |
| --- | --- | --- |
| 未设置 | `192.168.65.1` | http |
| `loopback` | `192.168.65.1` | http |
| `1`（hop count） | `192.168.65.1` | http |
| `172.16.0.0/12` | `192.168.65.1` | http |
| `192.168.65.1`（实际网关） | `203.0.113.9` | https |

除了运维指出的 `loopback` 失效，**hop-count 写法同样不生效**。只有显式写出代理的实际源地址才行。

而该地址依环境而变：Docker Desktop 是 `192.168.65.1`，docker0 是 `172.17.0.1`，compose 自建网络实测是
`172.20.0.1`。文档不能给默认值，只能给查询命令。

**修法**：`app.ts` 加 `trustProxy: process.env.TRUST_PROXY || false`；compose 里该变量设为必填（`:?`）；
`.env.example` 留空并附查询命令。

## 二、埋点 IP 绕过 trustProxy，可被任意伪造（本轮新发现）

排查第一条时发现的，**运维与文档双方的判断都不成立**。

`visitor.ts` 的 `clientIp()` 原本自己读 `X-Forwarded-For` 的第一段：

```ts
const forwarded = req.headers['x-forwarded-for'];
const raw = Array.isArray(forwarded) ? forwarded[0] : forwarded;
if (raw) { const first = raw.split(',')[0]?.trim(); if (first) return first; }
return req.ip || null;
```

它完全绕开 Fastify 的 trustProxy。所以：

- 运维说的「访客 IP、GeoIP 继续错误」不成立——IP 不会记成代理地址
- 真实缺陷是**任何人直连都能把埋点 IP 写成任意值**，`trustProxy` 配什么都拦不住

实测：`TRUST_PROXY=0.0.0.0/32`（不信任任何代理）下，直连伪造 `X-Forwarded-For: 198.51.100.77`，
`page_views.ip_truncated` 落库为 `198.51.100.0`。

**修法**：`clientIp()` 改为只取 `req.ip`，由 Fastify 先校验来源可信再解析该头。

修后同一实验：

| `TRUST_PROXY` | 落库 `ip_truncated` |
| --- | --- |
| `0.0.0.0/32`（配错） | `172.20.0.0` ← 网关地址，一眼可辨 |
| `172.20.0.1`（配对） | `198.51.100.0` ← 真实客户端 |

这也给了运维要的验收口径：**看埋点表里是不是公网地址**。配错会记成内网 `172.x`。

代价：`TRUST_PROXY` 配错时 IP 记成代理地址。这是配置错误、验收可发现，好过静默接受伪造值。

`vitest.config.ts` 补 `TRUST_PROXY: 'loopback'`——`inject()` 的 socket 是 `127.0.0.1`，
信任它才能让测试里的 `X-Forwarded-For` 走与生产一致的解析路径。327 条测试全绿，断言一条没改。

## 三、备份 —— 产品决定不做

第一轮曾按运维意见做了 `scripts/backup.sh`（卷名问 compose 要、staging 目录原子发布、
`pg_restore -l` + `tar tzf` 双校验、sha256、rclone 异地、失败告警），并实测通过完整灾难演练。

**第二轮审核后产品明确决定：不做备份。** 脚本已删除，两份文档里的备份与恢复章节整节移除，
默认无备份。

保留两条实测记录，将来若重新引入备份可省一次踩坑：

1. `echo "...（卷 $UPLOADS_VOL）"` —— 全角右括号紧跟变量名，bash 把它的首字节当成变量名的一部分，
   报 `UPLOADS_VOL: unbound variable`。要用 `${UPLOADS_VOL}` 界定。
2. `docker compose exec -T postgres pg_restore -l /dev/stdin < file` —— exec 的 stdin 传二进制会被截断，
   校验必然假失败。要把文件挂进一次性容器用路径读。

### 由此产生的后果，已写进文档

无备份不是单纯少一个功能，它改变了回滚的可行性：

- **没有新迁移的版本**：仍可回滚，切旧 tag 重建即可
- **带新迁移的版本**：**无法回滚**。迁移只前进没有 down 脚本，而通常的兜底「还原升级前的数据库快照」
  在没有备份时不存在。切回旧代码也没用——旧代码对着被改过的表结构跑，且启动时会再次执行那些迁移

唯一出路是前滚修复。因此升级流程第一步强制先 `git diff --stat <旧>..<新> -- drizzle/`，
有输出就意味着这次升级单向不可逆，上线前需业务方确认。

写在 deployment.md 第 7 节、operations.md 第 8 节，以及两份文档的开头。
operations.md 另加了「永远不要用 `docker compose down -v`」的警告——在无备份前提下它等于一键抹掉全部数据。

## 四、升级、回滚流程不可靠

运维列的五项全部成立，改法：

- 先 `build` 再 `down`，构建失败不影响在跑的旧容器（原来「先 build」只是可选建议）
- 上一版本写进部署目录（`.deployed-version.prev`）而非 `/tmp`
- 不再写死 `origin/master`，也不再部署分支 HEAD：**统一按 tag 部署**，与职责边界里「开发打 tag」对齐。
  分支会动，tag 不会，出问题时「线上是哪个版本」必须有确定答案
- 回滚用 `git switch --detach`
- 带迁移时不可回滚，见第三条

基础镜像可变 tag 的问题**未完全解决**，见「遗留」。

## 五、GitLab Token 用法泄密

运维正确。且第一版文档的前提就错了：**仓库早已有 remote，而且是 SSH**：

```
origin  git@gitlab.195322.xyz:chromeextentions/others/link-profile.git
```

文档照抄了 `CLAUDE.md` 里过时的「no git remote」，没跑 `git remote -v` 核实，据此编了一整套
HTTPS + token 流程。整段删除，改为 Deploy Key（SSH）。

## 七、健康检查说明错误

运维正确。`restart: unless-stopped` 只对进程退出生效，healthcheck 报 unhealthy 不会触发重启。
compose 里补了注释说明它只提供状态可见性与 `depends_on` 判据；自动拉起要靠外部监控，写进 operations.md。
另加了 json-file 日志轮转（`max-size: 10m`、`max-file: 5`）。

## 八、Nginx 版本兼容

`http2 on;` 需 ≥ 1.25.1。文档补版本声明、老版本写法、`nginx -t` 与 reload，以及运维点名要的登录限速配置。

## 九、事实与表达错误

| 问题 | 处理 |
| --- | --- |
| 称仓库没有 git remote | 实际有，且是 SSH。见第五条 |
| 称 `X-Forwarded-Proto` 影响 session cookie 的 `Secure` | 错。`sessions.ts:67` 只看 `NODE_ENV`。结论（走 HTTP 登不上）对，机制写错，已改 |
| 环境变量表缺 `APP_PORT`、`GEOLITE2_HOST_DIR` | 补 |
| `PUBLIC_ORIGIN` / `SUPERADMIN_PASSWORD` 表格与 compose 的 `:?` 矛盾 | 统一为必填 |
| 数据库密码直接拼进 URL | `.env.example` 要求只用字母数字，附 `openssl rand -hex 32` |
| `sudo mkdir -p /srv` 后 clone 权限失败 | 改为 `install -d -o "$USER"` |
| `curl -s` 遇 503 仍退出 0 | 统一改 `curl --fail-with-body -sS --max-time 10` |
| 超管忘记密码只写「进库改」 | 补完整流程，已实测 |

超管应急重置实测：用运行镜像里的 argon2 生成哈希（参数与应用一致）→ UPDATE → 旧密码 401、新密码 200。
**并发现一处必须补的步骤**：直接改库不触发 `deleteSessionsForUser`，旧 cookie 改密后仍返回 200，
必须一并 `delete from sessions`，清完才 401。

## 第二轮审核

第一轮整改送审后运维复核，确认核心修复已落地（Dockerfile、compose、`.env.example`、`trustProxy`、
`req.ip`、构建、门禁、端口绑定全部通过），并列出三个阻断 + 七个其他项。逐条处理：

| 项 | 处理 |
| --- | --- |
| **阻断 1** `scripts/backup.sh` 用 `docker compose ps -q app` 查容器，默认不返回已停止容器，导致「停 app 再备份」的严格一致流程必然失败 | 已实测复现（报「app 容器没在运行」）。改用 `ps --all -q` 后通过；随后备份整体取消，见第三条 |
| **阻断 2** 带迁移回滚顺序危险：恢复流程末尾会启动 app，而此时仍是新代码，会立刻重新执行新迁移 | 成立。取消备份后问题转化为「带迁移不可回滚」，见第三条 |
| **阻断 3** `docker compose down` 删除默认网络，重建时网关可能变，`.env` 里仍是旧地址，`TRUST_PROXY` 静默失效；且文档用 `$(basename $PWD)_default` 猜网络名，与自己「项目名可被覆盖」的判断自相矛盾 | 成立。compose 加固定网段 `172.28.0.0/24` / 网关 `172.28.0.1`，`.env.example` 填同一个值并注明两处必须一致。排查命令改为从运行容器 `docker inspect` 取网络名，不再拼目录名 |
| 磁盘 15 GB 未给容量公式 | operations.md 第 2 节补容量构成与 uploads 估算式（1000 账号 10% 视频 ≈ 1.6 GB）。因不做备份，原本要算的 30 份全量副本不再存在 |
| 超管重置用 `-e NEWPASS=` 把明文放进 Docker CLI 参数，`ps` 可见；且写死账号 `admin` | 改为 `printf | docker compose exec -T` 走 stdin；先查 `select account from users where role='superadmin'` 再按查到的账号更新 |
| 票里写「`pnpm test` 327/327」，裸命令实际会失败 | 门禁一节改记完整可复现命令 |
| 职责写「开发发版本 tag」，升级流程却部署上游分支 HEAD | 统一为按 tag 部署，见第四条 |
| 新服务器可能没有 `~/.ssh` | Deploy Key 步骤前补 `install -d -m 700 ~/.ssh`；另加 `docker info` 权限预检 |
| `PG_IMAGE` 读 `.Config.Image` 得到可变 tag | 曾改为读 `.Image` 镜像 ID；随备份脚本一并删除 |
| `backup.sh` 先转正文件再生成 checksum，中断会留下正式文件 | 曾改为 staging 目录整体 rename 发布并实测通过；随备份脚本一并删除 |

阻断 3 的固定网段已实测：`down` / `up` 一轮后网关仍是 `172.28.0.1`，埋点记到真实客户端 IP
`198.51.100.0`。

## 遗留

1. **无备份**（产品决定，见第三条）。数据只存在于宿主机 docker 卷，磁盘损坏、误删卷、`down -v`
   均不可恢复。
2. **带迁移的版本无法回滚**。是第 1 条的直接后果，不是独立缺陷。要解除需要其一：引入备份、
   给迁移写 down 脚本、或改为向后兼容的两阶段迁移。
3. **基础镜像用可变 tag**（`node:22-bookworm-slim`、`postgres:18-alpine`）。回滚重建旧提交不保证拿到同一镜像。
   彻底解决要按 digest 固定，或改为构建产物/镜像存档分发——后者与「服务器直接构建」的部署形态冲突，
   需要产品侧先定方向。
4. **登录接口无限速**。当前只能在 Nginx 层兜底，应用侧应引 `@fastify/rate-limit`。
5. **单副本约束**未解除。迁移随启动执行且无 advisory lock，多副本会并发跑 DDL。
