# 15：数据保留与日聚合

**构建内容：** 埋点明细不会无限堆积把数据库撑爆，但历史图表也不会因为清理而断档。

- [x] 日汇总永久保留，跨越清理边界的历史图表数据连续不断档

## Comments

**实现记录（2026-08-27）**

- 日汇总一行 = 一个用户 × 一天 × 一组维度取值（国家、城市、设备类型、操作系统、来源），维度全留着，因此聚合之后按任一维度拆分的查询照样答得出来，只是失去了单条明细的时刻。
- **维度列用空串表示「未知」而不是 NULL**：Postgres 的唯一索引不把两个 NULL 当作相等，用 NULL 的话 `on conflict` 去重会失效，聚合任务重跑就会产生重复汇总。有一条测试专门盯这个。
- 幂等靠两件事：聚合走 `on conflict do update` 累加而不是新插一行；**聚合与删除在同一个事务里**，因此不会出现「加过一遍但没删掉」的中间态，重跑也就不会把同一批明细算第二次。测试连跑三次断言结果不变。
- 用原生 SQL 而不是查出来在 Node 里分组：半年的明细可能是几百万行，没有理由搬进内存。
- 定时器进程内跑，启动时先跑一次、之后每天一次，不额外起 cron 容器——任务幂等，多跑一次没有代价。

**一个需要知道的取舍：日汇总按 UTC 日切。** ticket 要求的就是「日汇总」，所以照做了。但 14 的展示时区切换是按用户所选时区切天与分桶的，因此**对超过六个月、已经聚合掉的数据，展示时区的切天边界与 24 小时分布图只能由 UTC 日近似还原**——比如选 America/New_York 时，老数据的「某一天」实际是 UTC 的那一天。近半年的数据走明细，不受影响。要让老数据也精确，得把汇总粒度改成 UTC 小时（一行 = 用户 × 小时 × 维度），存储量约为现在的 24 倍上限但实际远小于此。这个改动没做，因为它偏离了 ticket 明确写的「日汇总表」。
