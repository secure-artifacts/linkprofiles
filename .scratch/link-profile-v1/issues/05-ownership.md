# 05：归属分权与无归属流转

**构建内容：** 管理员从此只看得见自己创建的用户，别的小组的账号与数据一概不可见。某个管理员被删除时，他名下的用户不会变成没人能管的孤儿，而是转为无归属并在后台显眼可见，等待超级管理员重新指派。

**阻塞项：** 04 三级角色与用户管理

**状态：** ready-for-human

- [x] 用户持有可空的归属管理员外键；创建者自动成为归属管理员
- [x] 管理员的**每一个**接口都只返回归属于自己的用户，包括列表、详情、编辑、删除与数据分析
- [x] 管理员访问非名下用户的任一接口均被拒绝
- [x] 超级管理员不受归属限制，可见全部用户
- [x] 删除管理员后，其名下用户的归属置空而非连带删除
- [x] 无归属用户仅超级管理员可见，后台以显眼状态呈现，可重新指派给某个管理员
- [x] 改动集中在 04 建立的授权检查点，不逐个接口重复实现过滤

## Comments

**实现记录（2026-08-27）**

- 归属过滤确实只改了 `auth/policy.ts` 两处：`visibleUsersFilter` 里管理员那一支从 `undefined` 收紧为 `eq(users.owningAdminId, actor.id)`，`canTouchUser` 里加上 `&& target.owningAdminId === actor.id`。路由一行没动就全部生效了——这正是 04 建检查点想换来的东西。
- 收紧当天 04 的两条测试立刻变红（管理员改不动、删不掉那个 fixture 用户），因为 fixture 建的是无归属用户。这是对的：无归属用户管理员本就不该碰得到。改的是 fixture 而不是实现。
- 「创建者自动成为归属管理员」对超级管理员同样成立——超管建的用户归属超管本人，因此不会混进「无归属」清单里等人指派。无归属只由「归属管理员被删除」产生，语义干净。
- 归属置空靠外键 `on delete set null`，不是应用层补偿逻辑，所以删管理员这条路径不可能漏。
- 重新指派走 `PUT /_api/users/:id/owner`，**故意不走 `loadTargetUser`**：那条路径按定义看不见无归属用户，而这里要操作的正是它们。改用 `user:assign` 能力（仅超级管理员）单独把关，并校验目标必须是真管理员，不能塞用户或超管的 id 进去。
- `GET /_api/users?owner=none` 单列无归属用户供后台做显眼状态。可见范围仍叠在上面，管理员调它只会拿到空数组。
