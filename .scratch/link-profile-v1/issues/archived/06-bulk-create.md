# 06：批量创建用户

**构建内容：** 管理员从表格里复制多行粘贴进来，一次建好几十个账号。个别行有问题不影响其余行，结果会直接告诉他第几行为什么失败，不必整批重来。

**阻塞项：** 05 归属分权与无归属流转

**状态：** ready-for-human

- [x] 接受制表符分隔的四列输入：用户名称、账号、short_name、密码
- [x] 逐行处理：合法行照常创建，失败行跳过，不做整批回滚
- [x] 返回结果列出每个失败行的行号与原因，例如账号已存在、short_name 非法、密码为空、列数不对
- [x] 批量创建的用户归属于操作者
- [x] 全部密码以 argon2 哈希入库
- [x] 行解析逻辑作为 shared 包内的纯函数实现，并有覆盖各类畸形输入的单元测试

## Comments

**实现记录（2026-08-27）**

- 行解析是 shared 里的纯函数 `parseBulkUserRows`，只做无 I/O 的切列与格式校验；「账号已存在」这类要查库的判断留在路由里逐行做。单测覆盖了列数不对、账号/密码为空、非法 short_name、空行、`\r\n` 与 `\r` 换行、值里带空格等畸形输入。
- **行号按原始输入计数**，空行被跳过但不重排后面的行号——报错说的第 7 行就是用户在表格里看到的第 7 行。
- 逐行提交，不开事务包整批：失败行之前建好的照常留在库里，有测试直接断言这一点。
- 同一批内部的重复也挡得住（第二行撞第一行刚建的账号），先到先得。

**代码复查后补记（2026-08-27）**

复查发现一个真 bug：批量创建**没有检查墓碑**，因此绕道批量导入可以抢注一个已删除用户的 short_name，而单个创建会拒绝。根因是本 ticket 与 `04` 各写了一份 `findConflict`，16 加墓碑检查时只改到了 `users.ts` 那一份。

已合并成 `packages/server/src/users/conflicts.ts` 一处判定，单个创建、改名、批量创建共用；批量侧只负责把错误码翻成带具体值的人话。补了一条测试：先建再删使地址进墓碑，然后断言单个创建 409、批量创建同样失败并给出「永不再分配」的原因。
