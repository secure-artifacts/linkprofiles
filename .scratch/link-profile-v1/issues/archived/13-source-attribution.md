# 13：来源追踪与透传

**构建内容：** 同一个页面可以带不同参数投到不同平台，后台就能回答「哪个平台带来的线索最多」这个问题。需要时还能把来源传给按钮指向的目标网站。

**阻塞项：** 12 埋点写入、07 个人页内容编辑

**状态：** ready-for-human

- [x] 个人页地址可携带 src 参数，其值随该次访问的页面浏览与点击一并记录
- [x] src 值受字符集与长度限制，超出即丢弃，脏值不得进入数据库或后台图表
- [x] 无参数访问记为未知来源
- [x] 按钮可逐条开启来源透传，开启后跳转目标 URL 上会带上来源
- [x] 超级管理员可设置透传的全局默认值
- [x] src 清洗实现为 shared 包内的纯函数，并有覆盖注入类畸形输入的单元测试
- [x] 已知取舍需在后台文案中说明：使用 src 而非 utm_source，第三方站点的分析工具无法直接归因

## Comments

**实现记录（2026-08-27）**

- 透传的开关是「逐条 OR 全局默认」：按钮自己开了就透传，没开则看超级管理员设的全局默认。全局设置放在一张单行表里（`settings`，主键固定 `singleton`），不是键值对——设置项少且各有类型，键值对会把类型丢给每个调用方现解析。
- `appendSource` 有三条边界：来源为空不改地址；`mailto:` / `tel:` 这类非 http(s) 不挂参数；目标本来就带了 `src` 就不覆盖（用户手写的优先）。三条都有测试。
- 已知取舍的文案放在 shared 的 `PASSTHROUGH_CAVEAT` 常量里，由 `GET /_api/settings` 一并返回，后台直接显示在开关旁边。测试断言它确实提到 utm_source 与第三方站点——**接进后台 UI 在 11**。
- 社媒图标同样支持逐条透传，与按钮同一条规则。

**测试里踩到的一个真实行为，值得记下来**：`app.inject()` 默认的 User-Agent 是 `lightMyRequest`，isbot 会把它认成爬虫因而不写任何埋点。这是**正确的**——认不出是真浏览器的 UA 本就该按爬虫处理——但意味着任何断言埋点落库的测试都必须显式带一个真实浏览器 UA，否则会莫名其妙拿到空表。

**代码复查后补记（2026-08-27）**

复查指出 `src` 的处理与 requirements 有一处未记录的偏离：需求写「限 `[a-z0-9_-]`……超出即丢弃」，严格照做则 `?src=TikTok` 应整条丢弃记为未知来源，而实现里先 trim 再压小写才判定字符集，于是 `TikTok` 与 `tiktok` 归到同一个来源。

**决定保留这个行为**，并已在 `source.ts` 的文档注释里写明。理由：投放物料上的大小写不受我们控制，严格丢弃会把一批真实访问记成「未知来源」，反而污染了这个维度；而大小写不敏感并不会让任何脏字符进库——字符集判定仍然发生在归一化之后。若后续认为必须严格照字面执行，改动点只有 `sanitizeSource` 里的一行 `.toLowerCase()`。
