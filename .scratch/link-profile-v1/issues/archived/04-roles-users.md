# 04：三级角色与用户管理

**构建内容：** 超级管理员可以创建和删除管理员，管理员可以创建和删除用户。每个角色能做什么由一个集中的授权检查点裁定，而不是散落在各个接口里各判各的。

**阻塞项：** 03 超级管理员初始化与登录会话

**状态：** ready-for-human

- [x] 三种角色落地：超级管理员、管理员、用户
- [x] 超级管理员可创建、删除管理员；管理员不能创建管理员
- [x] 超级管理员与管理员均可创建、删除用户
- [x] 创建用户时四个标识字段各就各位：账号唯一、用户名称可重复、short_name 按小写唯一、显示名可重复
- [x] short_name 校验：强制小写，限 a-z 0-9 与连字符，3–30 位，不以连字符或下划线开头结尾
- [x] **全部受保护接口经由同一个授权检查点裁定权限**，为 05 的归属过滤留出唯一改动点
- [x] 越权调用返回未授权，且不因资源是否存在而给出不同响应

## Comments

**实现记录（2026-08-27）**

- 授权检查点是 `packages/server/src/auth/policy.ts` 一个文件，三部分：`can()` 只看角色能力、`canTouchUser()` 裁定「能不能对这个具体的人下手」、`visibleUsersFilter()` 给列表查询返回可见范围的 SQL 片段。路由侧只调 `requireCapability()` 与 `loadTargetUser()`，不自己判。05 的归属过滤只需改 policy.ts 里两处，文件里已标注。
- `loadTargetUser()` 把可见范围过滤直接拼进 SQL，因此越权目标在查询层面就取不到，与「目标不存在」「id 格式不合法」三种情况的响应完全一致——测试直接断言三者响应体逐字节相同，不构成存在性探针。

**与 ticket 措辞的一处偏离：** ticket 写「越权调用返回未授权」，实现里未登录是 401、登录了但不该碰是 403。理由是后台 SPA 要能区分「该跳登录页」和「该提示无权限」，越权一律 401 会把管理员误踢下线。ticket 的实质要求（拒绝 + 不泄露存在性）由 403 同样满足，且两种失败给的是同一个响应体。

- short_name 校验作为 shared 包内的纯函数（`validateShortName`），server 与后台共用同一条规则，单测覆盖了长度、字符集、首尾连字符、下划线开头、URL 不安全字符与非 ASCII。「强制小写」的口径取「压平后校验」而非「拒绝大写」，因此后台传 `MixedCase` 会入库成 `mixedcase` 并正常可达。

**代码复查后补记（2026-08-27）**

复查指出 requirements 的权限矩阵有一行**从未实现**：「重置、修改用户密码｜超级管理员 是｜管理员 仅名下」（用户故事 39）。此前只有需要验旧密码的自助改密码接口。17 张 ticket 的 checklist 都没列到它，因此一路没被发现。

已补 `PUT /_api/users/:id/password`：不验旧密码（场景就是「他忘了密码」），因此**只有管理员与超级管理员能调**，用户角色一律 403——否则用户就能用它绕开自助改密码的旧密码校验。改完踢掉该用户的全部会话。归属过滤复用同一个检查点，跨组管理员调它同样被拒（已加进 05 的越权用例集）。后台在用户列表加了「账号设置」，同时承载改 short_name（故事 41）与重置密码。
