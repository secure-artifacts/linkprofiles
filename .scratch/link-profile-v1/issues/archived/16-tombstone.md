# 16：short_name 墓碑与删除流程

**构建内容：** 用户被删除后，他印在名片上、挂在社媒简介里的旧链接不会把访客导到另一个陌生人的页面上。

**阻塞项：** 05 归属分权与无归属流转、10 媒体上传与处理

**状态：** ready-for-human

- [x] 删除用户时其 short_name 迁入墓碑并**永不释放**
- [x] 访问墓碑中的 short_name 返回 404
- [x] 新建用户或修改 short_name 时不得占用墓碑中已有的值
- [x] 删除用户时其上传的媒体文件从磁盘移除，不留孤儿文件
- [x] 删除用户时其埋点数据保留，历史汇总不断档

## Comments

**实现记录（2026-08-27）**

- 删除流程的三步顺序是有讲究的：**墓碑与删除在同一个事务里**，中途挂掉不会出现「用户没了但地址被放出去」的窗口；**磁盘清理放在事务之后**，因为文件删了没法回滚，而残留一个目录远比丢掉一条数据轻。
- 墓碑与 `users.short_name` 同一口径（都已强制小写），因此大小写不同也抢不到，有测试守着。
- 埋点表刻意不设指向 users 的外键（12 里就是这么建的），所以删用户时埋点自然保留，不需要额外做什么。测试直接断言删完之后 page_views 还在、userId 还对得上。
- 管理员没有 short_name，因此删管理员不产生墓碑；名下用户转无归属由外键 `on delete set null` 负责（05）。

**代码复查后补记（2026-08-27）**

复查发现墓碑检查**漏了批量创建这条路**——本 ticket 只在 `users.ts` 的 `findConflict` 里加了 `isRetired`，而 `bulk-users.ts` 有一份平行的实现。「新建用户或修改 short_name 时不得占用墓碑中已有的值」因此在批量导入这条路上不成立，旧物料上的链接可能被后来者接走，正是本 ticket 要防的那件事。

已把两份实现合并成一处（`src/users/conflicts.ts`），并在 06 补了针对批量路径的测试。教训记在这里：**同一条规则有两份实现时，后续加约束一定会漏掉一份。**
