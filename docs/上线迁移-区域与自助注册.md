# 上线迁移：区域归属与邀请码自助注册

本次发布把「归属管理员」从用户身上的一列改成「用户 → 区域 → 管理员」这条链
（ADR-0017），并加上邀请码自助注册与 reCAPTCHA。数据库要跑 5 个迁移，其中
**0021 会删掉一列，不可回退**，所以备份不是可选项。

对应迁移：`0020` — `0024`。

**先确认线上停在哪一版。**上面这个区间是相对 `0019_page_language` 说的。若生产还在 v1.0.0，
它停在 `0017`，本次要跑的是 `0018` 至 `0024` —— `0018` 与 `0019` 只是给 `users` 与 `profiles`
各加一列带默认值的语言字段，没有数据搬迁，本文的步骤照样适用，只是执行结果里会多出这两行。
用下面这条查线上实际停在哪：

```sql
select name from __migrations order by name desc limit 3;
```

| 迁移 | 做什么 | 风险 |
| --- | --- | --- |
| `0020_yielding_ares` | 建 `regions` 表，给 `users` 加 `region_id`，并把存量归属搬过去 | 有数据搬迁，是本次唯一一个会改动存量行的迁移 |
| `0021_wet_nemesis` | 删掉 `users.owning_admin_id`，加检查约束 `users_region_matches_role` | **删列，不可回退** |
| `0022_secret_lady_ursula` | 建 `invite_codes` 表 | 纯建表 |
| `0023_modern_drax` | `settings` 加 `registration_enabled`，默认 `false` | 纯加列 |
| `0024_equal_surge` | `settings` 加 `recaptcha_site_key` / `recaptcha_secret_key`，默认空串 | 纯加列 |

0020 的搬迁规则：每个管理员按「用户名称，为空则账号」得到一个默认区域，重名时
往后追加序号；归属于某个管理员的用户落进他的默认区域；原本无归属、或归属指向
超级管理员的用户落进固定主键为 `00000000-0000-4000-8000-000000000001` 的
「未分配」区域。超级管理员不拥有区域。

## 1. 先备份

0021 删列之后，没有 down 脚本能把 `owning_admin_id` 变回来。回退只有一条路：
从备份恢复。备份没验过就等于没有。

```bash
# 逻辑备份，自定义格式，便于单表恢复
pg_dump --format=custom --no-owner --no-acl \
  --file="linkprofile-$(date +%Y%m%d-%H%M).dump" "$DATABASE_URL"

# 立刻验一遍能不能读回来，只看目录不落盘
pg_restore --list "linkprofile-$(date +%Y%m%d-%H%M).dump" | head
```

上传的媒体不在库里，走的是 `UPLOADS_DIR` 那个卷，本次迁移不碰它，但同一次维护
窗口里一并快照更省心。

### 顺手留一张归属快照

0021 之后就查不到原始归属了。搬迁对不对，事后要有东西可比：

```sql
create table _premig_owner as
select id, role, owning_admin_id from users;
```

这张表在第 3 步用完就删。

## 2. 执行迁移

迁移器是幂等的：已执行的记在 `__migrations` 表里，重跑不会重放。每个迁移各自
一个事务，中途失败只回滚那一个。

**并发是唯一的坑**：`applyMigrations` 没有取咨询锁。多个实例同时启动会一起抢，
后到的那个会在主键冲突上抛错并退出。所以先把副本数降到 1，或者干脆用下面的
独立命令跑完再起服务。

```bash
# 独立跑（推荐）。仓库根目录，MIGRATIONS_DIR 必须给绝对路径
set -a; . ./.env; set +a
MIGRATIONS_DIR="$PWD/drizzle" pnpm db:migrate
```

Docker 镜像里 `MIGRATIONS_DIR` 已经是 `/app/drizzle`，直接进容器跑：

```bash
docker run --rm -e DATABASE_URL="$DATABASE_URL" <image> node dist/db/migrate.js
```

成功时打印：

```
已执行迁移：
  0020_yielding_ares.sql
  0021_wet_nemesis.sql
  0022_secret_lady_ursula.sql
  0023_modern_drax.sql
  0024_equal_surge.sql
```

服务启动时也会自动跑一遍（`packages/server/src/index.ts`），所以上面这步跳过也
能上线，只是失败信息会混在启动日志里，而且踩到上面那个并发问题。

**不要新旧版本同时连一个库。** 0021 把 `owning_admin_id` 删了，旧版本的用户列表
查询会直接报错。滚动发布要先停旧的，再迁移，再起新的。

## 3. 验证迁移跑成功了

### 3.1 上线前：在库的副本上跑自动化测试

仓库里有针对 0020 与 0021 的迁移测试，它们先跑到上一版、灌一批旧形状的数据、
再跑目标迁移，覆盖了重名、撞名、无归属、归属指向超管等分支：

```bash
docker compose -f docker-compose.test.yml up -d
TEST_DATABASE_URL=postgres://linkprofile:linkprofile@localhost:55432/link_profile_test \
  pnpm vitest run packages/server/test/migration-0020.test.ts \
                  packages/server/test/migration-0021.test.ts
```

真正要防的是生产数据里的意外形状，所以正式操作前先把备份恢复到一个临时库，
对着它跑一遍第 2 步，看有没有报错。

### 3.2 迁移后：查这几条

```sql
-- 五个迁移都记上了
select name from __migrations where name >= '0020' order by name;

-- 每个用户都有区域，管理员与超级管理员都没有；两条都必须是 0
select count(*) from users where role = 'user' and region_id is null;
select count(*) from users where role <> 'user' and region_id is not null;

-- 每个管理员恰好一个默认区域；应当返回 0 行
select owner_admin_id, count(*) from regions
where is_default group by owner_admin_id having count(*) <> 1;

-- 「未分配」还在，且无归属
select id, name, owner_admin_id, is_default from regions
where id = '00000000-0000-4000-8000-000000000001';

-- 归属逐人一致：应当返回 0
select count(*)
from _premig_owner p
join users u on u.id = p.id
left join regions r on r.id = u.region_id
where p.role = 'user'
  and r.owner_admin_id is distinct from (
    select a.id from users a
    where a.id = p.owning_admin_id and a.role = 'admin'
  );

-- 自助注册默认关着，reCAPTCHA 两把钥匙是空的；刚迁移完应当是 f / t / t
select registration_enabled, recaptcha_site_key = '' as site_empty,
       recaptcha_secret_key = '' as secret_empty from settings;
```

最后一条都对上之后：

```sql
drop table _premig_owner;
```

### 3.3 界面上再走一遍

1. 用超级管理员登录，打开「区域」：每个管理员各有一个带「默认」标记的区域，外加
   一个「未分配」。
2. 打开「用户」：区域那一列都有值，没有空的。之前归属于某个管理员的人还在他名下。
3. 用管理员登录：只看得到自己名下区域里的用户，别人的搜不到也列不到。
4. 「全站设置」里自助注册是关着的。要开的话得先在同一页填上 reCAPTCHA 的两把钥匙，
   否则注册页不会放行。
5. 后台静态资源是新构建的产物（`packages/admin/dist` → 镜像里的 `/app/public/_admin`），
   确认页面上有底部悬浮的筛选条与语言切换器上的国旗，没有就是旧资源没换掉。

## 回退

0022 — 0024 都是加表加列，旧代码不读它们，单独留着无害。真正挡住回退的是 0021。
一旦跑过 0021 又要回到 `0019`，只能停服务、从第 1 步的备份恢复整库，期间产生的
数据会丢。所以维护窗口里先做完 3.2 的核对，再放流量进来。
