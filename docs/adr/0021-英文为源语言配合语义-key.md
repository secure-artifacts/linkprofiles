# 英文为源语言配合语义 key

这个项目从第一行代码起就是中文优先：文案、注释、commit、文档全是中文，后台约 830 行内联中文字符串。接入 i18next 时最省力的做法是让中文继续当源语言 —— key 直接写中文原文，其余六种语言作为译文挂在下面。**没有这么做。英文是源语言，key 是语义标识，任何语言缺译文时回落英语。**

## 中文当源会卡在译者那一环

要支持的是菲律宾语、西班牙语、巴西葡萄牙语、印尼语、越南语。这些语向的译者绝大多数从英文翻，中文当源等于每加一种语言都要找一个中文到该语种的译者，而这类译者既少又贵。英文当源之后，源文是通用中转语言，加语言的门槛从「找得到人」降回「找得到时间」。

回落链定在英语而不是中文，是同一个理由的延伸：译文不全时，菲律宾用户看到英文兜底还能连蒙带猜，看到中文兜底等于什么都没有。

## key 用中文原文会让改标点变成全语言失效

以原文当 key 的方案里，源文既是内容又是标识。把「确定删除这个个人页？」改成「确定删除该个人页？」，六份译文的键全部失配，静默回落到源文 —— 界面上什么都不报，只是悄悄变回中文。语义 key（`profiles.delete.confirm`）把这两件事分开：改文案只动值，key 不动，译文继续命中。

编号 key（`msg_0142`）也能做到这点，但代价是代码里读不出这句话是什么，审查和改动都要反查表。不值得。

## 代价要认

- **这是本次改造里最大的一块体力活**：既要把现有中文逐条搬进 `zh-Hans`，还要为每一条新写英文源文。两件事都不能自动化到可以不看的程度，因为后台有大量领域术语（线索、条目、来源、地址变更流水），机翻会译乱。
- 中文从此不再是「改代码时顺手改的那个字符串」。改一句文案要动 key 与七份文件，比现在麻烦。这是多语言的固有成本，不是这个方案独有的。

## Consequences

- 译文集中在一个新的 i18n 包里，位于依赖链最底层，交给译者时指得出明确的交付范围。
- key 由英文源文推导出联合类型，拼错在类型检查阶段就失败；另有一个测试遍历六份译文，校验 key 集合与源文完全相等且无空串。两道门禁都跑在现有命令里，不新增工具链。
- 服务端拿不到语言上下文时一律英语，覆盖 404 页、登录失败报错、外部联系方式更新 API 报错三处。
- **品牌专有名词不进译文目录。** WhatsApp、Telegram、TikTok 这类词七种语言写法相同，继续作为结构化数据留在社媒平台清单里；七份都写一遍只会给译者制造把品牌名译错的机会。需要翻译的是描述性文案，例如输入提示和非品牌的平台名。
