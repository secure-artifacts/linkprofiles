# 账号与个人页拆分为两张表

`CONTEXT.md` 原本写死了「每个用户恰好拥有一个个人页」，`users` 表因此是「账号 + 个人页」合一：`short_name`、`display_name`、`bio`、`layout`、`theme`、三个 media id、`background_overlay` 与登录凭证挤在同一行。用户提出一个账号要能建多个个人页（同一个人给不同平台投放不同的页面，各自看数据），这条不变式就不成立了，只能拆表。

拆分后 `users` 退回纯账号表（8 列：id / role / account / password_hash / label / owning_admin_id / 两个时间戳），个人页的一切进新的 `profiles` 表。除 `sessions.user_id` 外，`buttons` / `social_icons` / `media` / `page_views` / `clicks` / `daily_summaries` / `short_name_tombstones` 上的 `user_id` 语义上一直是「个人页 id」而非「账号 id」，全部改指 `profiles`。

## Considered Options

- **保留一张表，加一列 `profile_index` 做复合主键**：不用迁数据，但每张关联表的外键都要变成复合键，且「账号」和「个人页」在代码里仍然分不开，权限判断（哪些动作用户自己做得了、哪些留给管理员）会一直纠缠。放弃。
- **新建 `profiles` 表，主键重新生成**：语义最干净，但 6 张关联表的外键值全要重写，`media` 的落盘目录 `{userId}/{mediaId}/` 也得跟着搬，迁移从 DDL 变成一次全量数据搬运，出错就是丢数据。放弃。
- **新建 `profiles` 表，主键复用 `users.id`（选定）**：见下。

## 关键手法：`profiles.id` 复用 `users.id`

回填时 `INSERT INTO profiles (id, user_id, ...) SELECT id, id, ... FROM users WHERE short_name IS NOT NULL` —— 新个人页直接沿用被迁移那一行的 `users.id` 当自己的主键。

由此，关联表里已有的外键**值一个字节都不用改**，迁移退化成近乎纯 DDL：DROP 旧外键 → RENAME 列 → ADD 指向 `profiles` 的新外键。`ADD CONSTRAINT` 会全表校验，有孤儿就整个事务回滚，不会静默丢数据。

副作用是收益：媒体落盘目录是 `{profileId}/{mediaId}/`（那个参数一直传的是个人页目标 id），因为 id 复用，**磁盘上的目录一个都不用挪**，迁移后仍然对得上。

代价是这条复用只对**存量**成立：迁移之后新建的个人页，`profiles.id` 与任何 `users.id` 都无关。代码里绝不能出现「拿账号 id 当个人页 id 用」的假设 —— 那种写法在开发库上会碰巧跑通，在新建的数据上必然错。

## Consequences

- 迁移 `0008_split_profiles_from_users.sql` 手写，七段，顺序不可调换；第 2 段回填后紧跟一段 `DO $$ ... RAISE EXCEPTION` 自校验行数，对不上就整事务回滚。drizzle-kit 的自动 diff 会生成破坏性迁移（直接 drop 列、建空表），不能用。
- **不可逆**：第 7 段 DROP 掉 `users` 上那 9 列。回滚只能靠备份。
- `analytics/queries.ts` 与 `retention.ts` 走原生 SQL，TypeScript 拦不住这次改名，只能手工逐处核对。最危险的一处是 `retention.ts` 的 `on conflict (profile_id, day, ...)` —— 漏改不报错，只会让 upsert 匹配不到已有行，每次重跑插新行而不是累加，日汇总被静默污染。`retention.test.ts` 里「可重复执行、重跑不重复计数」那条用例是这个错误的唯一防线。
- 墓碑语义随之变化：「删用户 → short_name 进墓碑」变成「删个人页 → 该地址进墓碑」+「删账号 → 名下全部地址一并进墓碑」。`short_name_tombstones.former_user_id` 改名 `former_profile_id`。管理员/超级管理员没有个人页，删除时不产生墓碑，行为不变。
- 路由契约变化：个人页内容读写从 `/users/:id/profile` 迁到 `/profiles/:id`（含 `/buttons`、`/social-icons`、`/media`）；新增 `GET|POST /users/:userId/profiles`、`PATCH /profiles/:id/short-name`、`DELETE /profiles/:id`。`/users` 响应不再拍平个人页字段，改为账号字段 + `profileCount`。
- `POST /users` 仍接受 `shortName`/`displayName`，在一个事务里创建「账号 + 第一个个人页」—— 批量创建的四列 TSV 契约因此不用变。
- 分析接口的可见范围由 `resolveVisibleProfileIds` 解析：`profileId` 看单页、`userId` 看该账号名下合计、都不给则是可见范围内全部。它在 `visibleUsersFilter` 外面多 join 一层 `profiles`，**不重新实现一遍三级可见范围** —— 漏一处就是越权。
- 一个账号允许有 0 个个人页（把最后一个删掉即可）。这不是异常态：账号仍能登录，只是后台列表是空的，可以自己再建一个。删除确认里对此有明示。
- **用户自助的边界**（本次一并定下，见 ADR-0010）：建页面、改地址由用户自己做得了；删页面留给管理员。`canTouchUser` 里用户那一支从「除了改 short_name 都行」的黑名单改成了 `SELF_SERVE_ACTIONS` 白名单 —— 以后加新动作时默认拒绝，得有人显式想清楚才放进来。
- `MAX_BUTTONS_PER_USER` 改名 `MAX_BUTTONS_PER_PROFILE`，语义从「每用户 50 个」变成「每个人页 50 个」，值不变。
