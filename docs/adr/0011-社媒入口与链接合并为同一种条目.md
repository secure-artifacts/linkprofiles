# 社媒入口与链接合并为同一种条目

社媒图标原本是「页面头部一排 36px 的小圆图标」，按钮是「主体区域的竖排卡片」，两张表、两个接口、两套渲染。用户要求把社媒改成一行一个的大卡片、并且能自定义标题与描述 —— 那正是按钮现在的形态。改完之后两者在页面上一模一样，`CONTEXT.md` 里「社媒图标与按钮的区别在于展现形式和位置，不在于行为」这句话的后半截还在，前半截没了。

区别只剩下一处：地址从哪来。链接由用户直接填 URL，社媒入口存平台 id 与用户填的号码/用户名，地址读时由 `buildSocialUrl` 拼。这一处差异不值得两张表、两个接口、两套「带 id 更新 / 不带 id 新建 / 没出现就删」的对称代码。

## Considered Options

- **保持两张表，社媒表加 `title` / `subtitle` 两列**：改动最小、零迁移风险。但两个概念在行为与渲染上已经完全一致却继续分立，两套写库逻辑继续重复，而且社媒条目的逐条点击明细仍然是缺的（要单独再写一个查询）。放弃。
- **合并成一张表（选定）**：`social_icons` 并入 `buttons`，用 `kind` 判别。表名不改 —— 改表名要连带动外键名与索引名，白付一次迁移成本。

## 关键手法：社媒行的主键原样搬进 `buttons`

`clicks.target_id` 是裸 uuid、**没有外键**。只要搬运时保留原主键，那张表一行都不用动：

```sql
INSERT INTO buttons (id, profile_id, kind, ...) SELECT id, profile_id, 'social', ... FROM social_icons
```

这条自带一层保险：万一两张表的 id 曾经撞过（概率上不可能），主键唯一冲突会让整个迁移事务回滚，不需要额外写校验。

`clicks` 因此零迁移。读取侧只删掉 `queryButtons` 里那个 `and c.target_kind = 'button'` 条件 —— 只剩一张表了，`target_id` 能 join 上就说明点的是这一行。历史上 `target_kind='social'` 的点击自动归位，**社媒条目第一次有了逐条点击明细**（那本来是个功能缺口，不是这次改动引入的）。

## Consequences

- 新迁移 `0010`，十段，顺序不可调换；数据搬运之后、焊死约束之前插一段 `DO $$ ... RAISE EXCEPTION` 自校验：行数一致 / 逐字段原样搬运 / 形状不变式 / 视觉开关回填 / position 连续无洞。
- **不可逆**：最后一段 `DROP TABLE social_icons`。回滚只能靠备份。
- **`position` 必须重排**。两张表原本各自从 0 编号，合并后同一个 profile 内会撞（走查库里 lena 的 5 个按钮与 5 个社媒都占 0–4）。重排规则是社媒在前，对应它们原本在页头的位置。
- `title` 回填成平台名（WhatsApp、Telegram……）。label 只存在于 TS 常量里，SQL 里抄了一份 14 个平台的快照 —— **这是撰写迁移那一刻的快照，不是长期同步**，迁移之后 title 就是普通可编辑字段。
- 新增 `kind` 枚举 `button_kind('link','social')`。**故意不与 `clicks.click_target` 共用类型**（那边历史取值是 `button`）：内容层不该反过来依赖分析层。写埋点时映射一行即可。
- 加 CHECK 约束 `buttons_kind_shape_chk`，写进 schema.ts 而不是只写在迁移 SQL 里 —— 只写在 SQL 里的话 `db:generate` 下次不知道它存在，代码里也读不出这条不变式。drizzle 推出的插入类型允许 `url`/`platform`/`value` 同时为空，TS 拦不住畸形行，这条约束是最后一道墙。
- 数量上限**没有被挤成一份**：`kind='link'` 仍受 `MAX_BUTTONS_PER_PROFILE`（50）限制，社媒仍受内置清单长度与「同平台只能启用一次」限制。合表不该让原本能建 50 个链接的页面因为加了社媒而建不满。
- 顺带修掉一个既有隐患：`track.ts` 原先直接采信客户端传来的 `kind`。合表前靠「查错表就查不到人」间接兜住；合表后伪造的 `kind` 会让 `target_id` 与 `target_kind` 对不上。改为用数据库查出的真值。
- 接口从 `PUT /profiles/:id/buttons` + `PUT /profiles/:id/social-icons` 合并为 `PUT /profiles/:id/entries`，body 用 `discriminatedUnion('kind')`。`title` 在社媒分支是**必填** —— 那是产品要求；迁移时的 label 回填只解决存量的初始值。
- 编辑器的两个投放区合并成一个列表，`onDragEnd` 里「先判断拖的是社媒还是按钮」那套分支随之消失，是净简化。
- **测试库测不到这次迁移**：`createTestContext` 总是从空 schema 一次跑完全部迁移，那段自校验永远是 0 行对 0 行。为此给 `applyMigrations` 加了可选的 `upTo`（不传时行为不变），并写了 `migration-0010.test.ts`：先跑到 0009、灌一批旧形状数据、再跑 0010。**这是「历史点击不断链」的唯一防线**，已用变异测试确认它不是空跑（把搬运改成 `gen_random_uuid()` 时它立刻变红）。

## 一个如实的代价

启用了很多平台的用户，页面会**明显变长** —— 一行 36px 的图标变成 N 张全宽卡片。这是需求指定的形态，不是可以回避的副作用。
