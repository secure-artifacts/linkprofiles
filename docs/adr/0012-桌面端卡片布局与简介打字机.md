# 桌面端卡片布局与简介打字机

两件事凑在一起记：它们都往公开页加东西，而公开页的约束（ADR-0004 的零 hydration、LCP 敏感）比后台严得多。

## 桌面端卡片

改之前公开页**全站没有一个响应式断点**，只有 `.pp-shell { max-width: 480px; margin: 0 auto }`。宽屏上的结果是：一条窄内容贴在顶部，下面大片空白，背景图被 `cover` 拉到整个视口、糊得很明显。

关键发现是**不需要改宽度**。横向居中与卡片宽度早就有了，缺的只有三样：不让 `flex: 1` 把它拉满整屏、给它自己的底色与圆角让它读起来像一个物件、上下留白。

```css
@media (min-width: 768px) {
  .pp { padding: 56px 24px; }
  .pp-shell {
    flex: none;
    background: var(--bg);
    border-radius: 28px;
    overflow: hidden;
    box-shadow: inset 0 1px 0 0 rgb(255 255 255 / .08), 0 40px 100px -40px rgb(0 0 0 / .5);
  }
}
```

- 断点取 768px：最大的手机竖屏约 430px，远在其下，「移动端形态不变」没有例外。
- 卡片底色用 `var(--bg)`（主题渐变本身）而**不是白色**。`nocturne`、`harbor` 这类深底浅字的主题，文字对比度是照着 `--bg` 调的，铺一层白会让浅色文字直接看不见，还会撞上 `profile-ui` 里既有的对比度检查。
- `overflow: hidden` 顺手把 hero / banner 那种贴边头图的上圆角裁好，不用逐个布局去改。
- Cutout 布局后来因图片覆盖文字且高度依赖素材构图而下线，桌面卡片不再有抠像出血被裁的问题。

### 补记：背景图模糊打底后来做了

上面原本写着「模糊打底没有做，真要做是后续独立一步」。用户实机看过之后要求补上，于是补了，仍然只在 768px 以上生效。

```css
.pp[data-bg-image] { background-image: none; }
.pp[data-bg-image]::before {
  content: ''; position: fixed; inset: -48px; z-index: 0;
  background-image: linear-gradient(…遮罩…), var(--bg-image);
  background-size: cover; background-position: center;
  filter: blur(28px);
}
.pp-shell { position: relative; z-index: 1; }
```

三处不显然的地方：

1. **必须挪到 `::before` 上**。`filter` 加在 `.pp` 上会把卡片里的文字一起糊掉——`filter` 作用于整个渲染树，不只是背景。
2. **`position` 取 `fixed` 而不是 `absolute`**。`.pp` 有 `overflow-x: hidden`，按 CSS 规范这会把 `overflow-y` 从 `visible` 提升成 `auto`，`.pp` 因此是个滚动容器，会把放大后的绝对定位层裁掉。`fixed` 元素不受非 transform 祖先的 overflow 影响，而且正好复刻 `.pp` 原本 `background-attachment: fixed` 的锚定行为。
3. **先外扩再模糊**。`blur` 在边缘会采样到画面外的空白，直接糊会露出一圈渐隐的边，要往外扩一圈把它推出视口。

   第一版用的是 `transform: scale(1.12)`，**实机走查时发现它不够**：外扩量按比例算会随视口缩水，800×420 的矮窗口下每边只剩 25px，已经小于 28px 的模糊半径，漏边又回来了。要盖住的是模糊半径，那是个恒定像素值，本来就不该跟视口尺寸挂钩。改成 `inset: -48px`，每边恒定外扩 48px，与视口无关。

`.pp-shell` 因此必须显式 `position: relative; z-index: 1`：`::before` 是定位元素，静态内容默认画在定位内容之下，不排这一手卡片会被糊层整个盖住。

后台预览因此加了手机 / 桌面两档视口切换 —— 不然用户看不到这个形态。切换只改 iframe 的 CSS 尺寸：iframe 是独立的浏览上下文，里面的媒体查询按它自己的框求值，预览文档与 postMessage 协议一行都不用动。

## 简介打字机

ADR-0004 禁的是 **React hydration 与 React runtime**，不是所有客户端 JS —— 公开页早就内联了一段约 1.8KB 的原生 IIFE 做点击埋点与视频延迟播放。打字机走同一条路，不破边界。

**没有引第三方库**。typed.js 零依赖、3.2KB gzip，本来是合理选择，但整页 HTML 现在才 23KB，为一个装饰效果涨 14% 不值。逐字追加的逻辑本身十行就够。

两处关键决定：

1. **SSR 无条件输出完整简介**，只多一个 `data-tw` 属性（开关关着时属性不存在）。JS 做的是「把已经在 DOM 里的字先清空、再逐个放回去」，而不是「SSR 吐个空节点、靠 JS 从零拼出来」。没有 JS 时那段文字照常显示。页面本来就是 `noindex`，所以真正的关切不是 SEO 而是无 JS 降级与可访问性。

2. **清空前先钉住高度**（`el.style.minHeight = el.offsetHeight + 'px'`）。不钉的话，清空那一帧段落塌陷，底下整列条目往上跳一下 —— 正好是 ADR-0004 全部前提要守的 CLS。

尊重 `prefers-reduced-motion: reduce`：用 `matchMedia` 在 JS 里判，因为这是 JS 驱动的行为，CSS 媒体查询管不到它。这与 styles.css 里 `.pp-lead:hover` 那条 `@media (prefers-reduced-motion: no-preference)` 是同一个原则、不同机制。

**不用纯 CSS 的 `steps()` 方案**：那个技巧只对 `white-space: nowrap` 的单行文字成立，而简介会换行（`.pp-bio { max-width: 29ch }`，通常 2–3 行），基于 width 的揭示会变成斜向擦除，不是逐字打字。

后台预览侧**另写了一份**约 12 行的 `useEffect`，与 `client-script.ts` 里那段是刻意重复的两份：后者是零构建步骤的内联字符串，结构上就 import 不了模块，共享只能共享一半。预览本来也没有复刻视频延迟播放与点击埋点，两条运行时路径不 DRY 是既有前提。

**但速度那个数字是共享的**：`CLIENT_SCRIPT` 本身是模板字符串，`${TYPEWRITER_STEP_MS}` 插值即可，预览那份直接 import 同一个常量。两边打字速度不一致的话，预览就不再是预览。

用户实机看过后觉得 32ms 太快，改成 70ms（`packages/shared/src/render/typewriter.ts`）。简介上限 300 字，按这个速度写满要打二十多秒——**这是如实的代价**，觉得太久就关掉开关。数字是单一常量，要调很便宜。
