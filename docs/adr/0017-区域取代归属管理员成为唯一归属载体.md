# 区域取代归属管理员成为唯一归属载体

ADR-0005 把用户直接挂在创建他的管理员身上，可见范围由 `users.owningAdminId` 一个字段裁定。现在要按区域分组用户、按区域分发邀请码、按区域看数据，用户身上就出现了第二个归属维度。

选择让区域成为唯一的归属载体：用户挂区域，区域挂管理员，`users.owningAdminId` 删除，换成必填的区域外键。归属管理员降级为区域的属性，一个用户的归属管理员由「用户 → 区域 → 管理员」推导。区域名全站唯一，因为它会出现在注册页给注册者确认。

放弃的方案是两个字段并存。它改动更小，但允许出现「用户归属管理员 A、所在区域属于管理员 B」这种无法裁定的状态，`visibleUsersFilter` 要写两套条件。ADR-0005 说过归属分权「只留一处可漏」，两套过滤条件就是两处。

## Consequences

- `policy.ts` 仍是唯一授权检查点，但 `visibleUsersFilter` 从单字段等值变成一次 join，`canTouchUser` 的目标用户要先取到它的区域。所有越权测试要重写。
- 每个管理员被创建时随之得到一个删不掉的**默认区域**，初始名取自他的用户名称，冲突时追加序号，之后可改。这保证「管理员一定至少有一个区域可用」，不必在建用户流程里处理零区域。
- 超级管理员不拥有区域。全新安装时 bootstrap 建一个全站的「未分配」区域，超管建的用户先落这里。它同时接住迁移过来的原无归属用户，不多造一个概念。
- 归属管理员被删除时，其名下区域的归属置空变成**无归属区域**，仅超管可见可再指派——语义与 ADR-0005 的「用户转无归属」一致，只是粒度从用户升到区域。无归属区域的邀请码立即失效，不再招人。
- 迁移按 `owningAdminId` 把现有用户分到各管理员的默认区域，原本无归属的落进「未分配」。迁移后可见性与迁移前逐人一致，这是这次迁移的验收标准。
- 管理员只在自己名下的区域之间移得动用户；跨管理员移动仍走既有的 `user:assign`，只有超管做得了。
- **区域名全站唯一，代价是它成了一个跨管理员的存在性预言机**：管理员 A 看不见管理员 B 的区域，但拿 B 的区域名去建区域或改名会收到「名字已被占用」，据此可以逐个验证某个名字是否存在。这是全局唯一命名空间的固有代价，`account` 与 `short_name` 早已如此。之所以接受：区域名要在注册页展示给注册者，不能按管理员分命名空间，否则同一个名字会指向不同区域。泄露面止于「这个名字被占了没有」，取不到区域里的任何数据。
