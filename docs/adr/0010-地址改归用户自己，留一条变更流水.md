# 个人页地址改归用户自己，并留一条变更流水

原规则是「用户改不了自己的 short_name」，理由写在 `canTouchUser` 的注释里：避免手滑把已印在物料上的链接搞失效。做多个人页这轮需求时，我沿用了这条，把「建页面」也划进管理员专属那一档 —— 结果是用户登录进来只有一个只读的页面列表，而需求原文是「**用户**允许创建多个 profile」。审查把这个矛盾挑了出来，用户确认：建页面、改地址都归用户自己，改前二次确认说清后果，并在数据库留一条能回退的记录。

原规则的意图没有错，错在它把「防手滑」实现成了「不许做」。防手滑该由确认流程和可回退性来兜，而不是把能力收走。

## Considered Options

- **维持原状（管理员代改）**：与既有权限模型一致，但需求原文不成立，且每改一次地址都要找管理员，对一个自助工具来说是伪需求。放弃。
- **直接放开，不加任何保护**：满足字面需求，但那条原规则担心的事会真的发生 —— 手滑改掉一个印在几千张名片上的地址，且无从追溯改前是什么。放弃。
- **放开 + 二次确认 + 变更流水（选定）**：能力给用户，风险用「改之前看清后果」和「改错了能照着改回去」兜住。

## Consequences

- `UserAction` 从 4 个值扩到 6 个，拆出 `profile:create` 与 `profile:delete` —— 建页面与删页面不再共用一档。建页面不作废任何已发出去的链接（只是多一个地址），删页面则是全系统唯一不可逆的操作（地址进墓碑永不再分配、媒体从磁盘删除）。
- `canTouchUser` 里用户那一支从黑名单（`action !== 'update:shortName'`）改成 `SELF_SERVE_ACTIONS` 白名单。**这是安全相关的形态改变**：黑名单下每加一个新动作都会默默对所有用户开放，白名单下默认拒绝，得有人显式想清楚才放进来。
- 新表 `short_name_changes`：改前、改后、谁改的、什么时候。与 `short_name_tombstones` 是两回事 —— 墓碑记的是**删除**产生的、永不再分配的地址；流水记的是**改名**，旧地址会被释放，能改回来，也可能被别人抢注。
- 改名与写流水在同一个事务里。只写成一半的话，回退时就照不着旧地址了。
- **回退没有单独的接口**：拿一个旧地址再走一次 `PATCH /profiles/:id/short-name` 就是回退。冲突检查、墓碑检查都已经在那条路径上，开第二个入口等于把这两道检查抄一遍。回退本身也是一次改动，同样留痕。
- 改成当前值不算一次改动，不写流水 —— 否则反复点保存会刷出一串没有信息量的记录。
- 删页面时流水随 `profile_id` 的 `on delete cascade` 一并消失。页面都没了，它改过什么地址不再有意义；而那些地址此时已经全部进了墓碑，本来也回退不回去。
- 用户仍然**删不了**自己的页面。它是不可逆的那个，留给管理员，前端在页面列表的说明里写明了要找谁。
