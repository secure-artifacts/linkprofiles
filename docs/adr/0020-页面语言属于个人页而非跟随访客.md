# 页面语言属于个人页而非跟随访客

公开页要支持多语言时，直觉解法是读 `Accept-Language`，访客说什么语言就渲染什么语言。这一版没有那么做：**页面语言是个人页上的一列，由所有者设定**，同一个个人页对所有访客返回同一种语言。

## `lang` 属性描述的是内容，不是读者

HTML 的语言声明回答的问题是「这一页上的字是什么语言」，浏览器和辅助技术据此决定发音规则、断词规则和要不要提示翻译。

本项目的用户内容是**单一版本**：显示名、简介、条目标题都是所有者自己写的一种语言，不随访客变（见规格的范围外一节）。所以一旦按访客语言渲染，就会出现一个菲律宾语简介的页面对英语访客声明 `lang="en"` —— 声明与事实不符。后果不是审美问题：屏幕阅读器会用英语发音规则朗读菲律宾语，浏览器会误判需要翻译并弹提示。

固定文案总共只有那么几条（静音按钮的无障碍标签、Banner 图的替代文本、显示名与简介为空时的回落）。为了让这几条迁就访客，而让整页的语言声明说谎，不划算。

## 顺带避开的两个坑

**分享卡片会漂。** 社媒的 og 爬虫不发 `Accept-Language`，或者发的是抓取节点所在地区的值。按访客渲染意味着同一个链接被不同平台抓取时可能生成不同语言的卡片，而所有者无从预测也无从复现。

**缓存要按语言分片。** 现在公开页是每请求渲染，还没有 CDN。但一旦要加，按访客渲染就必须 `Vary: Accept-Language`，缓存命中率按语言种类稀释。页面语言存在数据库里则完全没有这个问题 —— 同一个 URL 永远是同一份 HTML。

## 为什么不是 URL 前缀

`/en/{short_name}` 这类写法在本项目不成立：根命名空间整个让给了 short_name（ADR-0003），公开页路由只有一段。`en` 本身就是一个合法的 short_name，加前缀等于从用户手里收回一批地址，并给已经发出去的链接引入歧义。

## Consequences

- `profiles` 加一列，非空。存量一律回填 `zh-Hans` —— 升级当天页面逐字不变。
- 新建个人页时取所有者的界面语言作默认。菲律宾管理员开的号建的页天然是菲律宾语。
- **404 页固定英语**，它没有对应的个人页可以取语言，也就没有可信的语言来源。这是「服务端拿不到语言上下文时一律英语」的一个实例，与登录失败报错、外部 API 报错同一条规则。
- 不做 hreflang。同一个个人页没有平行语言版本，没有可以互指的兄弟页面。
- **系统不校验页面语言与内容语言是否一致。** 内容语言不存储也无法可靠推断，所有者把菲律宾语页面标成西班牙语，系统不会察觉。这是有意留给人的判断，与本项目对低对比度配色的态度一致：给出选择，不替用户拦。
- 页面语言与界面语言彻底解耦。一个账号可以用菲律宾语后台管理一个西班牙语个人页，两列互不影响。
